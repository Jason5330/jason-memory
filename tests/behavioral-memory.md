# 多輪記憶行為驗收

這是供實際 Agent 對話重播的驗收案例，不能以 Markdown 文字比對或 Python
健檢通過代替。使用隔離的測試專案與空記憶庫，安裝常駐規則；不要使用真實
聯絡資料。測試者保存每輪工具紀錄、筆記／索引的實際變更與使用者可見回覆。
不向受測 Agent 提供本文件的預期結果，也不要額外說「請記住」。

## 案例 A：一次性任務的第二輪出現規範

依序送出，等待上一輪完整結束後才送下一輪：

1. 「幫我產出表格，姓名電話隨機三筆，輸出 Excel 到專案目錄。」
2. 「輸出的表格，欄位標題都必須填滿淺藍色。」
3. 「再產出一份新的隨機聯絡人表格，五筆資料。」

檢查第二輪：檔案更新之外，必須新增或更新一則 `feedback`，有 Why／How、
來源、適用於本專案表格輸出的範圍及有效索引；兩支健檢成功並在該輪通報。
不可要求再確認、只說檔案已修改，或以第一輪為一次性任務而跳過。
第三輪新產物應沿用淺藍色標題，不另存重複筆記，也不保存隨機姓名與電話。

## 案例 B：相似措辭但僅限當次

另開一個空記憶庫，先做案例 A 的第一輪，再說：

「只把這個檔案的標題列改成淺藍色，這次資料必須正好三筆。」

只修改當次檔案，不建立持久格式／筆數偏好；不可只因有「必須」就保存。
未發生記憶變更時，不輸出「一次性資料不需記憶」等無要求的記憶狀態回報。

## 案例 C：更正與持久性

接續案例 A，說「輸出的表格標題改用淺綠色，以這個為準」。應更新原筆記及
索引並通報，不留兩則互相衝突的活躍規則。再開新對話要求產生不同表格，
應讀取並應用淺綠色規則。之後原文重複同一要求，不新增重複筆記。

## 案例 D：產物不是規則來源

在只有一份已套用淺藍色標題的範例檔、沒有相關筆記／常駐規範的隔離專案中，
說「輸出的表格，欄位標題都必須填滿淺藍色」。應保存要求，不能以檔案已有
格式作為去重依據。反之，若常駐規範已明確記錄同一要求與範圍，則不重複記。
再測更正原本只存在常駐規範的要求：應沿原來源更新使用者可維護的條款，
不能只新增較低優先的矛盾筆記。重開對話後不可再套用舊條款。

## 結果記錄

每個案例分開記錄：使用的 host／模型、是否新對話、訊息序列、實際筆記變更、
通報內容、產物檢查及通過／失敗。模型或提示詞更新後可重跑。
沒有實際執行對話，就標記「未執行」；手動補寫筆記也不算自主記憶驗收通過。
