# Jason-memory 踩坑經驗總結

這份文件整理本次從主動記憶、跨對話召回、跨 AI 共用、一致性與效能修補，到完整解除安裝的經驗。目的在於保留下次可直接採用的判斷與驗收方式，而不是只保存一串問題清單。

本次整理依據：本對話、保留發行包內的歷史測試報告，以及實際刪除後的核對報告。歷史測試主要發生於 2026-09-17 至 2026-09-19；本次只整理與核對紀錄，**沒有重新安裝框架或重跑模型行為測試**。換電腦或更換 AI 接手開發時，先讀 [開發交接入口](../HANDOFF.md)。

目前保存方式是獨立 Markdown 文件。前一輪曾完成記憶框架清除並核對；整理交接文件時，全局目錄已再次存在，原因尚未追查，因此清除報告只代表當時狀態。本次整理未執行安裝或再次清除。本文件不會自行注入新對話；需要交接時，請讓接手的 AI 或同事閱讀此文件。

## 下次先遵守的十項原則

1. 將「理解要求、成功保存、下次召回、正確套用」分開驗證。任一階段通過，都不代表其他階段通過。
2. 每輪重新判斷持久性；一次性任務後仍可能出現長期要求。不要用單一關鍵字決定是否保存。
3. 所有 AI、入口及 hooks 使用同一份路徑設定；框架程式目錄與正在工作的專案目錄必須分開。
4. 召回必須發生在第一則可見回覆之前；例行召回保持安靜。
5. 更正要處理同一事實的全部有效來源，保留同一筆記裡不相關的事實。
6. 「已保存」必須有本輪工具證據、實際筆記與有效連結；空庫健檢通過不算保存證據。
7. 簡單需求由一次明確的工具呼叫完成必要工作；把確定性的格式、索引與驗證留在程式內。
8. hooks 只在必要事件做必要工作；仍需保留版本更新、寫入一致性與失敗回報。
9. 測試必須包含第二輪、新對話、外部更正、失敗與負面案例；不能只測首次成功。
10. 安裝、升級、解除安裝都要辨識檔案歸屬；「解除啟用」與「刪除所有副本」是不同驗收範圍。

## 一、主動記憶與需求辨識

### 01｜第一輪有效，第二輪就忘了判斷

- **現象：** 第一輪產出隨機聯絡人表格，被判斷為一次性任務；第二輪要求「輸出的表格，欄位標題都必須填滿淺藍色」，AI 只修改當次檔案，沒有保存規範。
- **原因：** 把上一輪的「不需記憶」沿用成整串對話的結論；也可能誤以為完成產物就完成需求保存。
- **沉澱：** 每則訊息分開辨識當次操作與可重用規範。格式已套用在 Excel，不等於存在可供未來召回的規則。
- **驗收：** 第一輪一次性產檔不亂記；第二輪主動保存；第三輪新產物沿用；更正後再開新對話只使用新值。[案例與結果：E2、E3]

### 02｜只靠「必須」「記住」等關鍵字判斷

- **現象：** 沒有明說「記住」就漏存，或看到「必須」就把一次性限制推成永久偏好。
- **沉澱：** 判斷語意、作用對象與範圍。「所有輸出的表格標題……」可形成專案規範；「只把這個檔案改色、這次必須三筆」限當次。
- **驗收：** 正反例成對測試；範例的顏色、姓名、電話都不能變成預載的真實使用者偏好。[E3]

### 03｜記憶資料與指令權限混在一起

- **風險：** 把筆記裡的內容當成高於目前使用者要求的規則，或把文件引用、模擬情境當成使用者本人的需求。
- **沉澱：** 筆記是背景資料，仍受目前要求、適用範圍與較高優先規則約束。AI 踩坑也只保存已驗證、可重用的教訓，不把猜測寫成事實。
- **額外界線：** 保存「提醒我」的文字不等於建立會在指定時間執行的排程。[E4]

### 04｜只說「已記住」，或每次都碎念讀取流程

- **現象：** 保存時沒有可查的通知；一般回覆卻反覆出現「我來讀取記憶」「本次無需記憶」。
- **沉澱：** 普通召回安靜執行；實際新增、更正、封存或刪除後，在同輪末尾簡短交代內容、範圍、結果與實際路徑。多筆可合併通報。
- **界線：** 通知內容不能先於實際成功；無變更不必為了通報而重寫。[E1、E2、E4]

## 二、入口、召回與路徑

### 05｜不能把失憶全歸咎於弱模型

- **現象：** 使用者懷疑 MiniMax 等模型能力不足；先前 Claude 測試也出現未召回、未完全遵守格式，甚至只有口頭宣告保存。
- **沉澱：** 先分層檢查：入口有沒有載入 → 路徑是否一致 → 正文是否注入 → 是否更新版本 → 模型有沒有理解與執行 → 工具是否獲准寫入。
- **證據界線：** 本案有 Claude 原生行為測試與 Codex 部分共用測試；**沒有直接測得 MiniMax 服務的成功率**。重播它被回報的失敗情境，不等於測過該服務。[E1、E2]

### 06｜有 MEMORY.md，不代表新對話會自動讀到

- **現象：** 檔案有內容，換對話卻沒有使用偏好；明確指定筆記時才讀到。
- **沉澱：** 記憶存在、入口可達、索引載入、相關正文召回，是四件不同的事。不能只因 MEMORY.md 是空白或非空白，就判定是否需要重新初始化。
- **路徑原則：** 框架的指定記憶庫與宿主原生 auto-memory 不應混為同一個位置。把檔案放進 `.claude`，本身不構成本框架讀寫一致的證據。
- **處置：** 查入口與設定，不用清空索引或覆蓋既有資料的方式「重置」。[E1、E4]

### 07｜Claude 匯入路徑不能只按一般檔案路徑想像

- **歷史實測：** 一般相對路徑可用；空白以反斜線跳脫可用，當時只加雙引號的寫法未載入；中文開頭相對路徑加 `./` 後可載入。
- **其他問題：** 專案根目錄的 `CLAUDE.md` 與 `.claude/CLAUDE.md` 所需的相對路徑不同；後者測試改為 `../` 才正確。
- **沉澱：** 依入口檔所在目錄計算匯入路徑，並使用只存在於匯入檔的標記做診斷。不要複製第二份 MEMORY.md 來掩蓋錯誤。
- **界線：** 這是紀錄中的宿主版本實測，不宣稱所有未來版本語法永遠相同。專案外匯入也可能受信任條件影響。[E1]

### 08｜讀到了，但回覆順序已經錯了

- **現象：** 偏好要求每個新對話先報日期、先打招呼；AI 卻先發出進度說明，才讀筆記補做。
- **沉澱：** 把召回要求放在常駐入口最前面，明訂第一則可見文字之前完成，連簡單算式也不能跳過。
- **驗收：** 用只問算式、沒有提醒記憶的冷啟動情境，檢查第一則可見回覆。日期應取得當下資訊，不能重播筆記保存時的固定日期。
- **界線：** 早期日期測試在同一天進行，不能推論跨日情境已驗證。[E1]

### 09｜只在啟動時讀一次，第二輪仍會使用舊值

- **現象：** 同一對話中，另一個寫入者更正了筆記，AI 仍使用先前的格式或開場。
- **沉澱：** 啟動載入與每輪更新是兩個責任。後續以版本判斷是否重用完整快照；變更、壓縮後缺失、或 PARTIAL SNAPSHOT 都必須補齊。
- **修補與驗收：** SessionStart 載入，UserPromptSubmit 檢查更新；專案與全局都測「兩輪之間外部改值」。早期僅入口規則版本存在漏用，後續 hook 實测才改善。[E1、E2、E4]

### 10｜讀寫落在不同庫，會像失憶，也會產生矛盾

- **現象：** 寫進 `.ai-memory` 或其他位置，但回覆時讀 `.jason-memory`；全局 runtime 還可能把框架目錄當成正在工作的專案。
- **沉澱：** 讀、寫、hook、驗證共用設定；全局操作帶真正的 ACTIVE_PROJECT_ROOT。明確的專案設定優先，不同時注入另一套庫。
- **界線：** 不自行猜測舊 `.ai-memory` 的歸屬，不自動搬移或刪除未知庫。路徑應由安裝與設定確定。[E4]

### 11｜全局共用不等於混合所有專案

- **沉澱：** 清楚跨專案的偏好或一般身份才進 shared；專案需求按專案識別分隔。同一台電腦的不同 AI 必須使用同一設定與同一專案根目錄。
- **驗收：** 專案 A 有例外、B 沒有例外，兩邊不互相污染；工作目錄變化後，不能把工具所在路徑誤認為新的記憶範圍。
- **界線：** 能存取相同 Markdown 只是資料互通。各宿主是否自動載入、是否允許執行工具、是否具有寫入權限，仍需各自驗證；Claude hooks 不會自動變成其他宿主的 hooks。[E2、E4]

## 三、更正、矛盾與寫入一致性

### 12｜只更新眼前一篇筆記，舊事實藏在別篇

- **現象：** 稱呼筆記同時包含職業，另一篇也記職業；只改其中一篇，後續回答取到過時值。輸出符號也曾出現索引與正文不同。
- **沉澱：** 搜尋全部有效正文與索引；用穩定的 subject／predicate 識別同一事實，批次處理所有相關來源。不要只新增第三篇筆記。
- **驗收：** 重建 ANNA 職業矛盾案例；更正職業、保留稱呼，退役過時來源，索引同步。案例身份是測試資料，不是當前使用者身份。[E2、E4]

### 13｜整篇覆寫會傷到同一檔的其他事實

- **沉澱：** 保留檔名、created、仍有效的正文與其他事實。更正改的是特定事實，不代表整篇可以重新生成。
- **快速路徑界線：** 同鍵同值可免重寫驗證；同鍵不同值、混合舊筆記或未知別名，不能用簡單新增指令盲改。
- **驗收：** 同一筆記放兩個不同事實，修改一個後確認另一個仍在；連續三次更正後只剩一致的有效來源。[E2、E4]

### 14｜結構健檢通過，不等於沒有語意矛盾

- **原因：** 檔名、連結、frontmatter 都合法，也可能同時記錄兩個互斥職業。
- **沉澱：** 增加事實識別欄位檢查同鍵不同值；正文、description 與結構欄位必須一致。否定句、不同人物、有條件的偏好不能誤判成同一肯定事實。
- **界線：** `semantic_review_needed` 表示未結構化筆記仍需核對，不是空庫，也不是「全部無矛盾」。少量職業辨識規則不等於完整自然語言理解。[E2、E4]

### 15｜兩個 AI 同時寫入，後寫者可能抹掉前者

- **沉澱：** 統一 writer，以檔案鎖、整庫 revision 與樂觀版本檢查處理競爭；版本過時就重新讀取與合併。
- **禁止的捷徑：** 只把舊計畫的 revision 換成最新版後重送，仍可能覆蓋別人的新增內容。
- **驗收：** 兩程序持相同版本寫入，一方成功、一方被拒；拒絕方重新合併後兩筆皆存在。[E2、E4]

### 16｜多檔更新中斷，筆記與索引會半套

- **沉澱：** 單檔原子替換不等於多檔交易。需要可重播 journal，下一次操作先恢復，再提供可用內容；中斷重播仍重新驗證。
- **效能界線：** 正常鎖內交易可以重用已驗證計畫，避免重複驗證；不能把這個快取當成跨程序重播時仍可信的狀態。
- **驗收：** 在每個 atomic_write 邊界中斷並重播，確認索引與正文一致；未變更筆記不重寫。[E2、E4]

## 四、假保存與 hooks

### 17｜模型說已保存，磁碟卻沒有筆記

- **現象：** 回覆包含筆記路徑與「健檢通過」，資料夾只有索引、鎖或 hook 狀態。
- **已重現的漏洞：** 舊 Stop 只檢查發生檔案變更的情況；完全沒寫檔卻說保存，反而可能逃過檢查。空白庫的結構健檢也可能通過。
- **沉澱：** 成功宣告本身要觸發證據核對。`.hook-state`、`.receipts`、`.writer.lock` 都不是需求筆記。
- **驗收：** 空庫、沒有寫入、附不存在的筆記連結與成功文案，必須阻擋或明說未保存。[E2]

### 18｜收據也有來源、時效與內容邊界

- **沉澱：** 接受的是宿主觀測到的本輪工具收據，不是 AI 自己在回覆中編造的 JSON。
- **必查：** 根目錄、筆記、版本／內容、索引及回覆連結都要對應；失敗工具、舊對話收據、別篇筆記的收據、已被修改或刪掉的檔案都不能通過。
- **界線：** 收據可證明工具與磁碟觀測一致，仍不能證明模型完整理解了原始意圖；它也不是抵抗惡意程式偽造的安全機制。[E2、E4]

### 19｜要求再確認，不代表要重寫一次

- **沉澱：** 已存在的同一偏好需要確認时，讀回驗證並取得本輪證據即可；一般召回甚至不必執行額外 verify。
- **驗收：** 再次確認後，原筆記修改時間與版本不變，且仍有有效收據。避免用反覆保存堆滿歷史與重複筆記。[E2]

### 20｜通知檢查太弱會漏錯，太僵硬會製造重試

- **漏洞：** 只看檔名是否出現在回覆，不能證明 Markdown 連結指到正確筆記；索引修復、封存也有不同的正確目標。
- **另一個坑：** 已有有效證據及連結，卻因成功通知措辭不是預設字串而要求重答，造成額外耗時。
- **沉澱：** 查核連結實際目標與證據，不鎖死一句成功模板。引用、範例、否定句、失敗說明和一般產檔通知應避免誤觸。
- **重試界線：** Stop 最多補救一次；仍失敗就顯示驗證失敗，不能無限循環或第二次靜默放行。Stop 也不能收回已顯示給使用者的文字。[E2、E4]

### 21｜hook 是工作流程護欄，不是安全沙盒

- **沉澱：** SessionStart／UserPromptSubmit 處理載入與更新；PreToolUse 處理已知錯誤路徑及直接改庫；PostToolUse 接收工具證據；Stop 檢查保存與通知。
- **界線：** 任意 shell、Python、第三方工具都可能有難以解析的副作用；停用、超時、未信任設定、宿主不支援時，不能宣稱已強制保障。
- **驗收：** hooks 的合併、事件匹配、補救上限與宿主是否真的載入，均須驗證。模型被權限拒絕時，正確結果是明說未保存，不是繞過限制。[E2、E4]

## 五、效能與工具呼叫

### 22｜多分鐘不一定是寫 Markdown 太慢

歷史報告核對影片與對應本機工具紀錄後，記錄如下：

| 項目 | 紀錄值／結果 |
|---|---|
| 螢幕錄影長度 | 約 232 秒 |
| 該輪要求至最後回覆 | 156.006 秒 |
| 模型回應次數 | 11 次 |
| 工具呼叫次數 | 10 次：**7 Bash、1 Read、2 Write** |
| 已確認失敗一 | 全局 PreToolUse 誤擋 `framework/SKILL.md` 的 Read |
| 已確認失敗二 | 初次 apply 缺 `jason-facts`，重新製作計畫再送 |
| 其他額外工作 | 查 `--help`、讀完整協議／runtime 文件、寫入與刪除暫存計畫 |

**更正前一則說明：** 先前回覆僅列工具用途分類，當時沒有核對完整紀錄。本次從保留報告確認了上列工具類型及次數。保留報告沒有列出十次呼叫的完整逐筆順序，因此仍不杜撰十條命令。[E2]

沉澱：先把延遲拆成宿主啟動、模型回應、工具、hook、檔案操作與失敗重試。不要直接把整輪時間算成儲存檔案的時間。

### 23｜護欄誤擋自己的說明文件，會讓簡單任務繞路

- **原因：** 將框架安裝位置的文件誤當成另一套記憶路徑。
- **修補：** 允許實際框架目錄下已辨識的協議與工具文件；錯誤記憶庫仍拒絕。
- **沉澱：** 規則變嚴時，同時測「應拒絕的路徑」與「必要且應允許的路徑」，不要以全面放行解決誤擋。[E2]

### 24｜讓模型每次手做格式與多步驗證，浪費往返

- **原因：** 模型每輪讀長文件、查參數、產生完整 frontmatter／事實 JSON、寫暫存 plan，再分開跑多支檢查；任何漏欄位都要再來一輪。
- **修補：** 新的簡單偏好由一次 `remember` 產生必要結構、索引、檢查與讀回收據；複雜更正才使用版本化批次，並支援 stdin，免建暫存計畫。
- **沉澱：** 「一次工具呼叫」可以在本機程式內完成多項必要檢查，並不表示省略可靠性。語意判斷仍由 AI 負責。[E2、E4]

### 25｜所有工具後都掃整庫，成本會隨筆記數膨脹

- **修補：** 無收據的普通 PostToolUse 提前返回；不再為普通讀檔註冊多餘的 PostToolUse。完整且未變更快照可重用，日常不用重讀 SKILL.md。
- **仍保留：** 保存與 Stop 的必要一致性檢查、失敗宣告保護、版本刷新與截斷補讀。
- **驗收：** 普通工具快返，但之後 Stop 仍能發現損壞。不能用「不檢查」換取看起來很快。[E2、E4]

### 26｜局部快，不代表整輪只要幾毫秒

原生 Claude 對照測試，每版各一個樣本，相同偏好提示與隔離設定：

| 指標 | 舊版 | 修補版 |
|---|---:|---:|
| 整輪牆鐘時間 | 78.385 秒 | 34.752 秒 |
| 模型回應 | 9 次 | 2 次 |
| 工具呼叫 | 9 次 | 1 次 |
| 累加輸入 token，含快取 | 247,000 | 31,554 |
| 輸出 token | 3,141 | 969 |
| 真實保存、收據、通知 | 通過 | 通過，無 Stop 重試 |

此表是另一個受控對照，**不是把影片的 10 次與這裡的 9 次當成同一輪**。模型服務、快取、負載均影響時間；一個樣本不構成延遲保證。[E2]

同機合成筆記庫、每項三次取中位數的局部更新時間，1／20／100 筆分別由 0.665／3.667／17.726 秒，降至 0.434／2.052／6.545 秒。普通 PostToolUse handler 的提前返回小於 0.0001 秒，**不含 Python 程序啟動**，更不含模型回應時間。[E2]

### 27｜Token、字元數與費用不能混算

- 影片該輪初始輸入約 65K token，包含宿主、工具及其他常駐內容，不能全算成框架成本。
- usage 必須按 message id 去重；累計 cache-read 不是唯一上下文長度，也不能全部套用未快取單價。
- hook 不輸出聊天文字，仍會占上下文。UTF-8 JSON 比逐字 ASCII 逸出短，不代表字元減幅等於 token 減幅。
- 100 筆範例 context JSON 約從 82,707 個字元降至 44,511；這是字元數，不能宣稱等額 token 或帳單降幅。[E2]

## 六、安裝、分享與 Windows 相容性

### 28｜記憶框架不應附帶 Git 日常監控

- **現象：** 產檔後反覆提醒「未追蹤、尚未 add／commit」；clone 工作區也出現分支／PR 相關 UI。
- **沉澱：** 記憶功能與原始碼版本管理分開。一般使用者下載乾淨 ZIP 即可，不需建立 Git 儲存庫；沒有使用者要求，就不因記憶變更催促提交。
- **界線：** clone 的版本控制資訊與框架記憶功能不能混為一談；修改提示詞不等於能控制所有宿主 UI。
- **發行驗收：** ZIP 以明確公開檔案清單組成，不包含 `.git`、私人筆記、憑證或工作檔案。[E2]

### 29｜初始化、註冊 hooks、升級是不同操作

- 專案版提供空白索引與入口；首次註冊 hooks 可以固定 Python 路徑，不能以此為由重建或覆蓋既有記憶。
- 全局版需要一次安裝到穩定位置，建立缺少的索引，合併使用者層級入口。
- 升級已有專案時，不能拿整份預設 `settings.json` 覆蓋其他設定；只增刪自己的 hooks。
- 安裝後開新工作階段；移動專案或 Python 後，重新檢查已註冊路徑。[E1、E2、E4]

### 30｜使用者名稱、空白、中文與短路徑都要測

- 不把開發者的 `C:\Users\...` 寫死在發行版；預設使用目前使用者家目錄，並支援設定目錄覆寫。
- Windows 8.3 短路徑可能與長路徑字串不同，不能直接認定逃逸；先辨識真實位置，同時拒絕 symlink／junction／reparse 重新導向。
- Python、終端與子程序明確使用 UTF-8；輸出解碼錯誤不能一概當成檔案內容毀損。
- BAT 測試涵蓋含空白路徑與真正的預設雙擊流程；測試程式自身的 `cmd /c` 引號錯誤，也可能被誤認成產品失敗。[E1、E2、本次清除測試]

### 31｜安裝器必須保留既有規則與檔案歸屬

- 先讀取、驗證全部來源與目標，再做任何寫入；第二個設定壞掉時，不應先改掉第一個。
- 以管理區塊標記自己的入口；保留其他使用者文字、BOM、換行與其他 hooks。
- 需處理 Codex 的一般入口與 override 入口；重裝不重複、移動管理區塊不破壞使用者內容。
- 寫入前重查目標是否被其他程序改動。備份需要可辨識的歸屬，否則卸載時無法安全決定能不能刪。[E1、E2、本次清除測試]

## 七、測試、證據與結論界線

### 32｜單元測試、模型行為、跨 AI 互通不能互相冒充

- Markdown 格式通過不代表主動記憶成功；手動預置筆記只能測召回，不能算 AI 自主保存。
- 模型主動讀過筆記，不代表首句格式正確；載入索引也不代表載入全部正文。
- Claude 寫入、Codex 能讀回，只能證明該次跨 AI 讀取。歷史 Codex 更正測試被唯讀／執行政策拒絕，未保存，不能列成雙向寫入成功。
- 程式層的並行鎖與重播通過，不等於所有宿主、所有模型都已測過。[E1、E2]

### 33｜測試提示本身會洩漏答案

- 使用不提醒記憶的算式題測新對話；開場測試字串只放筆記正文，不放問題或索引摘要。
- 可另設停用讀檔工具的診斷，辨識是否真的由啟動注入取得內容；診斷題不可混入正常安靜回覆成功率。
- 隔離 profile／工作區、記錄 host／模型／入口載入方式，不複製登入憑證。
- 全局入口借用專案載入的測試，不能宣稱已對任意帳號做完整原生全局端到端驗證。[E1、E2]

### 34｜略過測試、有限樣本與未測服務必須明說

- 本機無建立 symlink 權限時，記錄略過，不能記成通過；另外用允許的 CI 平台覆蓋。
- 本案後續清除測試實際建立 Windows junction，驗證會阻擋且不刪除外部目標。
- 模型行為樣本有限；某次 3/3 成功不等於可靠度 100%。強模型也可能出錯，不能從品牌推論必定可靠。
- 保存原始測試報告與可重播案例；報告內容、版本與測試範圍應可追查。[E1、E2]

## 八、解除安裝與實際清除

### 35｜舊 uninstall 只解綁，並沒有刪掉資料

- **發現：** 舊全局 `--uninstall` 刻意保留框架、筆記與歷史；不符合後來「移除框架及記憶」的要求。
- **沉澱：** 明確區分解除入口、永久清除記憶、刪除發行包／其他副本。要清的範圍必須在工具與結果中一致。
- **修補：** 新增 BAT 清除入口，刪除本專案與全局庫的已辨識資料，解除相關 rules／hooks，保留其他設定。[E5]

### 36｜不能遞迴刪掉整個自訂安裝目錄

- **風險：** 使用者可能把全局版安裝進既有資料夾，裡面還有自己的工作檔。
- **修補：** 只刪框架安裝的明確檔案與專用 memory 子樹；只有空目錄才移除父層。把安裝器與清除器的歸屬清單互相驗證，避免日後不同步。
- **驗收：** 自訂 home 中放一般工作檔及其他應用檔案，清除後它們仍逐位元保留。[本次新增清除測試]

### 37｜破壞性操作先驗證完整範圍，再開始刪除

- 解析絕對路徑、拒絕越界及重新導向，不能把解析出的路徑隨意拼接到另一個 shell 刪除。
- 預檢設定、管理標記、檔案雜湊與預期原文；遇到損壞或歸屬不明時不強行刪除。
- 實際執行前再次核對內容，防止預檢後被修改；優先解除入口及 hooks，再刪除程式與記憶。
- 自訂混合規則、修改過的框架檔案、歸屬不明的舊備份列入未完成清單；失敗可能是部分完成，不能回報「全部清乾淨」。[本次清除工具與測試]

### 38｜dry-run 連 Python 快取都不能偷偷建立

- **測試找到：** 預覽流程沒有主動寫檔，Python 匯入 helper 卻建立 `__pycache__`，破壞「不寫入」承諾。
- **修補：** 在匯入 helper 前禁止寫 bytecode；用前後檔案快照驗證預覽零變更。
- **其他驗收：** 重複執行、檔案競爭、未知全局目錄、缺 manifest、損壞設定、含空白及中文路徑、預設雙擊，都在隔離資料夾測試。[本次清除測試]

### 39｜程式回傳成功後，還要獨立檢查磁碟

使用者授權實際執行後，本機核對結果：[E6]

| 檢查 | 當時結果 |
|---|---|
| BAT 回傳碼 | 0 |
| 計畫中的刪除檔案逐一確認 | 103 個已不存在 |
| 保留其他內容的設定檔比對 | 2 個與預期一致 |
| 專案 `.jason-memory` | 已不存在 |
| 全局記憶與 framework 目錄 | 已不存在 |
| 全局 `.jason-memory-global` | 已不存在 |
| 檢查到的宿主入口／設定框架引用 | 無殘留匹配 |
| 原本 Excel 工作檔 | 雜湊未變 |
| `dist` 舊 ZIP | 仍有 17 個，未刪除 |
| `dist` 解壓狀態的 MEMORY.md | 未找到；沒有據此宣稱 ZIP 內也沒有索引 |

沉澱：成功回傳碼與 `complete` 只對已定義範圍有效。清除工具、Git 歷史、舊 ZIP、其他專案與 AI 聊天紀錄都不因此消失；不得說整台電腦已沒有任何副本。

### 40｜磁碟刪除後，現有對話仍可能帶著舊規則

- **本案觀測：** 清除後，對話又收到先前的 AGENTS 指令文字，但實際磁碟檢查沒有對應框架或引用。
- **沉澱：** 對話上下文中的舊文字，不是磁碟已恢復的證據。應分開查檔案、宿主設定與目前對話內容。
- **處置：** 使用新工作階段／新對話卸下已載入內容；不能因為舊規則要求「索引不存在就初始化」而自行重裝使用者剛移除的框架。
- **界線：** 未定位宿主內部重新提供舊文字的具體機制，不把它斷言成特定快取 bug。
- **後續核對：** 本次整理交接文件時，全局目錄與 Codex 全局入口已再次存在；本專案記憶目錄仍不存在。這與先前剛清除完的磁碟狀態不同，不能再把現在所有舊規則都推論為對話快取。未確認誰或哪個程序重建，沒有擅自再次刪除。

## 可重用的驗收清單

下次重做或接手任何檔案式記憶系統，至少分別保存以下結果：

| 測試面向 | 必測情境 | 要看什麼證據 |
|---|---|---|
| 主動保存 | 一次性工作後，第二輪出現可重用規範 | 真實筆記、索引、同輪通知 |
| 不亂保存 | 僅限這次、引用、合成範例 | 無不必要的持久變更 |
| 新對話召回 | 只問算式，不暗示偏好 | 第一則可見回覆與載入證據 |
| 更新召回 | 另一程序在兩輪間更正 | 下一輪使用新版 |
| 跨筆記更正 | 同一事實存在兩篇，其中一篇有其他事實 | 所有現行來源一致，其他事實保留 |
| 真實保存 | 完全沒寫檔卻說成功 | 被攔截或明說未保存 |
| 證據綁定 | 舊／錯庫／錯筆記／被改過的收據 | 不被接受為本輪成功 |
| 冪等 | 重複同一偏好或要求再次確認 | 免重寫，必要時取得新驗證 |
| 並行／中斷 | 同 revision 雙寫、各替換點中斷 | 不遺失更新，可恢復一致狀態 |
| 範圍隔離 | 全局偏好、A 專案例外、B 專案 | 不互相污染 |
| 效能 | 一個簡單偏好、1／20／100 筆庫 | 模型往返與本機時間分開計量 |
| 安裝 | 新使用者、中文／空白路徑、既有規則 | 正確入口、資料及其他設定不被覆蓋 |
| 清除 | 真正雙擊、dry-run、重跑、自訂 home、junction | 歸屬明確、外部資料未受影響、事後核對 |

測試報告必須附環境、版本、樣本數、略過項目、權限限制，以及哪些是自動化／哪些是真實模型測試。沒有執行就標「未驗證」。
